# AGENTS.md

## What this is

Single-file script `uxplay_presence.py`: spawns uxplay itself as an audio-only AirPlay server (`-p`, `-vs 0`, `-md`, `-ca`), watches the metadata file uxplay writes, mirrors Track / Artist / Album plus elapsed/remaining time to Discord Rich Presence (pypresence IPC), exposes the session as an MPRIS media player on D-Bus (`org.mpris.MediaPlayer2.uxplay`, `--no-mpris` to disable), and serves a "now playing" web page (`/`, `/state` JSON, `/art` JPEG, `/config` GET/POST for the presence-line mapping) on `127.0.0.1:8080` (`--ui-port`, `--no-ui` to disable), auto-opened in the browser (`--no-browser` to disable). No test suite, no lint/CI tooling — don't invent commands for these.

## Environment

- Python 3.14 venv at `.venv/` (repo has no pyproject; deps are exact-pinned in `requirements.txt`: pypresence, watchdog, dbus-next).
- Install: `.venv/bin/pip install -r requirements.txt`

## Verification

- Syntax check: `.venv/bin/python -m py_compile uxplay_presence.py`
- Behavior check: `.venv/bin/python uxplay_presence.py --dry-run` — logs payloads instead of talking to Discord, and does not require a client ID. Still spawns uxplay.
- Without an AirPlay device: `--dry-run --no-uxplay` plus a hand-written `Key: value` meta file (create the dir first) exercises watcher, payloads, and web UI; write/delete the file to test update/clear paths.

## Runtime prerequisites (not code)

- Requires `uxplay` on PATH (the script spawns it; override session with `--port` / `--name`; `--no-uxplay` attaches to an externally started uxplay instead).
- Discord desktop app must be running for IPC; client ID comes from `--client-id` or `$DISCORD_CLIENT_ID` (no bot token needed).

## Non-obvious constraints when editing

- Discord sends run in a dedicated sender thread inside `PresenceBridge` (FIFO queue): `update()`/`clear()` only enqueue, and the identity-skip, `--min-interval` throttle, retries, and reconnects all happen in that thread — the worker never blocks on Discord, so the pause watchdog, clears, and resume-restores stay real-time even while a send is deferred (the sender logs `rate limit, sending in Xs` at INFO and sends when due). Identity-skip compares title/artist/album/image plus a `has_timer` marker (so timer-less → timed transitions re-send) and deliberately excludes recomputed `start`/`end` values. Clears, resume-restores, and config-change refreshes use the `RESUME_THROTTLE` (2s) floor instead of the 15s interval — Discord tolerates these small bursts (~5 updates/20s). Dry-run honors the throttle too (it simulates real pacing).
- Logging cadence: uxplay's `audio progress` lines are logged at INFO (~1×/sec — the log's heartbeat; all other uxplay output is DEBUG), and the sender thread logs every Discord outcome (`presence updated` / `skipped (payload unchanged)` / `presence cleared`) at INFO.
- Playback pause/stream-end detection: progress lines stop when audio stops, so the worker clears presence when the last snapshot is older than `PAUSE_TIMEOUT` (5s) and auto-restores it when fresh progress reappears. Impossible in mirror mode (no progress lines at all) — there, clearing still happens via file deletion or uxplay rewriting the file to "no data".
- Discord field limit is 128 chars (`clip()`); values shorter than 2 chars are dropped.
- Duration/position do NOT come from the `-md` file (only string tags there). They are parsed from uxplay's stdout line `audio progress (min:sec): P:SS; remaining: R:SS; track length D:SS` (`\r`-terminated, ~1×/sec, minutes can exceed 59). That line only exists in audio-only ALAC streaming — mirror-mode AAC disables it, in which case the app degrades to no timestamps (worker waits up to 3s per track change, gives up permanently after 3 misses).
- Track-change updates accept a progress snapshot only when it matches the new-track signature (`new_track_signature`): a duration different from the pre-change track's, or a raw position that does not exceed the pre-change track's last printed position, or no prior progress (startup mid-track) — B's first print can never be later into its track than A's last print was into A's. Required because the old track's prints keep *advancing* after the metadata flip (auto-advance lag) and its final print lingers unresolved across the gap — Python's universal-newline reader cannot return a `\r`-terminated line until the next stdout byte arrives (the original wrong-timer bug). On timeout the update is sent without timestamps; the worker's idle tick re-sends with a timer once a fresh snapshot matches the signature and isn't identical to the rejected prior (`timer_pending`/`pending_prior`). Resume-restore keeps the advancement rule: raw position must change between two fresh snapshots (frozen = not actually playing). The identity-skip in `PresenceBridge` also compares a `has_timer` marker so timer-less → timed transitions re-send.
- Metadata file format is `Key: value` lines, keys lowercased; `title`, `artist`, `album`, `album artist`, `genre` are mappable to the four Discord presence slots (`name`/`details`/`state`/`large_text` — `large_text` is the image caption Discord renders as a 4th line, never auto-copied from `state`), plus a fixed-text option `apple music` that sends the literal "Apple Music". Defaults: `name`→apple music, `details`→title, `state`→artist, `large_text`→album. A fifth key `status_display` (`name`/`details`/`state`, default `state`) picks which line the member-list badge shows ("Listening to <that line>"; the card's first line always follows `name`, with fallback to `name` when the chosen line is absent from the payload). Configured in the web UI, persisted in `~/.config/uxplay-presence/config.json` (`--config` to override); a saved config missing the `large_text` key is treated as legacy and replaced by the new defaults on load (logged). Presence and UI clear when the file is deleted/renamed (uxplay deletes it on exit) or has no title — the watcher handles modified/created/moved/deleted events.
- MPRIS: `MprisServer` runs a dbus-next asyncio loop in a daemon thread and publishes Playing/Paused/Stopped (from the same events the worker feeds `AppState`), full `xesam` metadata, live `Position` (µs), and an `mpris:artUrl` chain (resolved artwork URL → local UI `/art` → `file://`). Control methods (Play/Pause/Next/…) raise `NotSupported` and `CanControl=false` — uxplay's raop is receive-only (`/rate`/`/setProperty` are client→server), so the AirPlay client cannot be commanded. dbus-next is imported defensively: missing library or no session bus just logs and disables MPRIS.
- Cover art: iTunes Search API first (artworkUrl100 rewritten to 1000x1000), fallback to catbox.moe upload; only successful URLs are cached per (title, artist) so failed lookups retry on later events. The upload is gated by `valid_art_bytes`: the file must be ≥ `MIN_ART_BYTES`, start with a JPEG SOI and end with EOI — uxplay writes a 95-byte 1×1 PNG placeholder into the `-ca` file on stream/codec changes, and the real cover often arrives after the metadata event, so `wait_valid_art` polls up to `ART_SETTLE_TIMEOUT` (5s) before uploading; uploading the placeholder was the "art never shows in Discord" bug. The web UI `/art` endpoint applies the same gate (404 on invalid).
