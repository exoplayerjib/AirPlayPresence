# AGENTS.md

## What this is

Project **AirPlayPresence** (GPLv3): single-file script `airplay_presence.py` that spawns `uxplay` itself as a headless audio-only AirPlay server (`-p`, `-vs 0`, `-md`, `-ca`), watches the metadata/cover files uxplay writes, and feeds three outputs: Discord Rich Presence (pypresence IPC, with elapsed/remaining timers), an MPRIS player on D-Bus, and a local web UI (`/`, `/state`, `/art`, `/config` on `127.0.0.1:8080`). No test suite, no lint/CI — don't invent commands for these.

## Environment

- Python 3.10+ (venv at `.venv/`, Python 3.14 here); deps exact-pinned in `requirements.txt`: pypresence 4.6.2, watchdog 6.0.0, dbus-next 0.2.3.
- Install: `.venv/bin/pip install -r requirements.txt`
- Regenerating the venv after moving the repo folder is required (venv scripts embed absolute paths).

## Verification

- Syntax: `.venv/bin/python -m py_compile airplay_presence.py`
- Behavior: `.venv/bin/python airplay_presence.py --dry-run` — logs payloads instead of talking to Discord (no client ID needed), still spawns uxplay and honors the send throttle.
- Without an AirPlay device: `--dry-run --no-uxplay` plus a hand-written `Key: value` meta file exercises watcher/payloads/UI. For seeks/timers, shim a fake `uxplay` on PATH that writes the meta file and prints the progress line (see below) — that runs the whole pipeline.

## Runtime prerequisites (not code)

- `uxplay` binary on PATH; Discord desktop app running; client ID via `--client-id` or `$DISCORD_CLIENT_ID`; a D-Bus session bus for MPRIS (missing → logged and disabled).
- AirPlay ports must be open (UDP 5353, TCP 7100/7000/7001, UDP 6000/6001/7011 — see README firewall section).

## Non-obvious constraints when editing

- **Discord sends run in a sender thread** inside `PresenceBridge` (FIFO queue): `update()`/`clear()` only enqueue; identity-skip, the `--min-interval` (5s default) throttle, retries, and reconnects live there. The worker never blocks on Discord — pause watchdog, clears, and resumes stay real-time. Clears/resume/refresh/seek updates use the `RESUME_THROTTLE` (2s) floor; dry-run honors the throttle too. **Coalescing**: the throttle wait happens *before* `_absorb()` drains the queue, so anything queued during the wait collapses — consecutive updates fold into the newest, an update followed by a clear folds into the clear, but a clear followed by an update is kept intact (dropping the clear would leave `_cleared` False and let the identity-skip swallow the resume update). Rapid skips are collapsed twice: the `--debounce` window (1.5s) merges the burst's metadata rewrites into one job that re-reads the final file, and coalescing catches anything that still queues together (e.g. a heartbeat racing an update).
- **Identity-skip** compares name/details/state/large_image plus a `has_timer` marker (timer-less → timed transitions re-send) and deliberately excludes recomputed `start`/`end` values. Bypass it only via `force=True` (seek and heartbeat updates use this). `large_image` carries a `fresh_image_url` `?v=` nonce, so for tracks with art the identity never matches and every metadata-driven send dispatches — the skip only guards art-less tracks.
- **Seek detection**: `ProgressState.set()` bumps `seek_seq` when a print jumps > `SEEK_FORWARD_JUMP` (4s) forward or > `SEEK_BACKWARD_JUMP` (2s) backward vs the previous print; the worker's idle tick then re-sends with `force=True`. Normal +1–2s steps never trip it. Fast-forward produces no metadata event — without this, the timer goes stale. A natural track transition *also* looks like a backward jump (position resets to 0), so the seek tick only reacts when no metadata change is in flight (`debouncer.last_schedule <= last_job_at`); suppressed seeks are consumed by the metadata job instead, which sets `last_seen_seek = progress.seek_seq` after sending.
- **Heartbeat keep-alive**: the worker's idle tick re-sends `last_payload` (`force=True`) every `--min-interval` seconds while a track is active — insurance against Discord silently dropping the activity. It reuses the last built payload (no metadata re-parse, no MPRIS churn; `start`/`end` are absolute epoch values so the re-sent payload stays correct) but re-resolves the art URL first (`ArtworkResolver.url_for` with `wait=False` — single non-polling file read) and rewrites `large_image` via `fresh_image_url` (a `?v=` nonce per send — litterbox ignores query params, Discord's proxy treats each variant as a new asset and re-fetches, so a flaked first fetch heals within one heartbeat instead of pinning the "?" placeholder for the URL's lifetime) — dropping the key entirely when the resolver returns None (expired link + failing refresh). MPRIS is republished only when the raw URL actually changed. The gate requires `HEARTBEAT_QUIET` (5s) since the debouncer last saw a metadata event (`Debouncer.last_schedule`), so a skip burst halts heartbeats from its *first* file write, not just from when the collapsed job fires. Idle-tick branch order: stale-clear → resume → seek → heartbeat → timer refresh.
- **Duration/position come from uxplay's stdout**, not the `-md` file: line `audio progress (min:sec): P:SS; remaining: R:SS; track length D:SS`, `\r`-terminated, ~1×/sec, minutes can exceed 59. Only exists for audio-only ALAC streaming (mirror-mode AAC disables it → degrade to no timestamps). That line is logged at INFO (the log's heartbeat); other uxplay output is DEBUG.
- **`\r`-newline trap**: Python's universal-newline reader can't return a `\r`-terminated line until the next stdout byte arrives, so the old track's final progress print lingers unresolved across track gaps. This is why the new-track signature (`new_track_signature`) requires duration ≠ prior or position ≤ prior's, and why resume requires raw position advancement — don't relax those. The reset usually lands *before* the debounced metadata job, so by then the raw snapshot is already the new track's and the signature could never match again — `send_update` therefore compares against `ProgressState.seek_base()` (the print from before the reset, kept fresh for `SEEK_BASE_MAX_AGE` 8s). Without it, every track after the first ships timer-less.
- **Pause watchdog**: presence clears when prints go silent > `PAUSE_TIMEOUT` (5s) and auto-restores on resume. Mirror mode has no prints at all — clearing there relies on file deletion or uxplay rewriting the file to "no data".
- **Discord field limit** is 128 chars (`clip()`); values < 2 chars are dropped.
- **Metadata file**: `Key: value` lines, keys lowercased. `title/artist/album/album artist/genre` map to the four presence slots (`name`/`details`/`state`/`large_text`), plus fixed-text options: `apple music` ("Apple Music") and `custom:<text>` (arbitrary literal string, picked via the web UI's "Custom text…" — blank text is rejected by `valid_source`); `status_display` picks the member-list badge line. Saved config at `~/.config/airplay-presence/config.json` (`--config` to override; legacy `uxplay-presence` dir auto-migrates).
- **Member-list rotation**: config keys `status_rotation` (bool), `status_rotation_order` (ordered subset of `STATUS_DISPLAY_OPTIONS`, only enabled lines), `status_rotation_interval` (s, clamped 10–600 at both ingest points). The web UI box lists the three lines in saved order (draggable HTML5 DnD, disabled ones grayed at the bottom) with per-line checkboxes and a "showing" badge fed by `/state`'s `status_line` (AppState.set_status_line, updated on every send). The worker steps `rot_idx` only inside the heartbeat branch when `interval` has elapsed — effective period ≈ max(interval, min_interval), active-presence only; index resets on restart. `send_update` and the heartbeat always stamp the current rotation line into `status_display_type` (overriding `build_payload`'s static `status_display` logic, which remains the fallback when rotation is off or the order is empty). Rotation is a payload-level change: status_display_type is in IDENTITY_KEYS, so these sends are never identity-skipped.
- **Cover art**: on this branch, upload-only by default — valid art goes to litterbox.catbox.moe with `time=1h`. Litterbox rejects non-browser User-Agents and rate-limited IPs with 412 ("No file!") — `_upload` sends a Mozilla UA for this reason. Every upload is verified before use: `_verify` HEAD-polls the returned URL until it answers 200 (up to `UPLOAD_VERIFY_TIMEOUT` 10s), because the litterbox CDN can lag behind the upload response — an unverified link is what let Discord pin the "?" placeholder for the URL's whole lifetime. Both the `ImageUploader` (per-digest) and `ArtworkResolver` (per-track) caches store `(url, timestamp)` and treat entries as expired after `UPLOAD_TTL` (1h, matched to litterbox's expiry) — no proactive refresh; the next lookup after expiry (usually a heartbeat) uploads a replacement link then. `--itunes-art` re-enables iTunes Search first (artworkUrl100 → 1000x1000) with upload fallback. On refresh failure `ArtworkResolver._last_fail` opens a `UPLOAD_RETRY` (60s) gate before the next attempt (heartbeats would otherwise retry every `--min-interval`); within the gate `url_for` returns the cached URL without network calls — but only while it is still within TTL: an expired link is never served (the heartbeat drops `large_image` instead — no art beats a broken "?" box). `valid_art_bytes` gates uploads (≥ `MIN_ART_BYTES`, JPEG SOI/EOI) because uxplay writes a 95-byte 1×1 PNG placeholder into the `-ca` file on stream changes and real art often arrives after the metadata event — `wait_valid_art` polls up to `ART_SETTLE_TIMEOUT` (5s); heartbeat lookups use `read_valid_art` (single read, no poll). Failed lookups are not cached as values (they retry after the gate). `/art` applies the same gate.
- **MPRIS**: dbus-next asyncio loop in a daemon thread; publishes metadata/status/position. Control methods raise `NotSupported`, `CanControl=false` — uxplay's raop is receive-only (`/rate`/`/setProperty` are client→server), the phone cannot be commanded. dbus-next is imported defensively: absent library or bus just logs and disables. GNOME queries `DesktopEntry` on the root interface — keep it present.
- **Discord rate limits**: ~5 updates/20s. The 5s cadence is the regular heartbeat (4 sends/20s — at the limit's edge; `ServerError` trips are absorbed by the sender's retry path, which sleeps `min_interval` and retries). Clears/resume/refresh/seek use the 2s floor. Don't remove either.
